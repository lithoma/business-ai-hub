# Company internal-server deployment

Current architecture: user Databricks OAuth → Hub routing/task extraction model →
Genie One for business analysis, SQL generation, qualitative trigger decisions and
report writing. Saved, reviewed trigger SQL is executed directly on the SQL
Warehouse with date bindings; it is not regenerated by an agent on each run.

The maintained application and all local file dependencies are in this Git. No
Databricks Workspace source-file download is needed at runtime. Archived cloud
resources live in `migration/` and must not be executed on startup.

## Readiness

Implemented and offline checked: personal OAuth/PKCE login, server-side sessions,
creator-bound tasks/reports/conversations, identity-bound SQL test receipts,
current-user business SQL/MCP calls, one Genie One adapter, and local manual trials.
Company multi-user live acceptance has not occurred. No deployment, grants,
endpoints, Job starts or company resources were changed.

Unattended execution still needs a company-approved credential broker that can
resolve a fresh **task creator** credential after the user leaves. `CreatorRunner`
in `creator_execution.py` accepts that resolver and checks its actual SDK identity.
Without it, the Task Manager fails with `CreatorAuthorizationRequired` before any
business query or report call. It never falls back to the Job/App Service Principal.
Browser OAuth sessions are memory-only, expire after eight hours and are not a
background credential vault. CSV exports for creator-bound tasks fail closed until
a creator-scoped export adapter is installed. Existing mail previews without CSV
remain available in the local launcher.

## Administrator inputs

| Input | Purpose |
|---|---|
| Company Workspace HTTPS URL | All user SQL, router and Genie One calls use it |
| Internal site HTTPS origin | Exact registered `/auth/callback` URL; DNS/certificate/reverse proxy |
| Custom OAuth app client ID; secret if confidential | Individual U2M login using SDK OAuth + PKCE |
| Enabled OAuth scopes | `iam.current-user:read`, `ai-gateway`, `sql:restricted-query`, `model-serving`, `offline_access`; confirm availability on the registered company app |
| SQL Warehouse ID | Users need access; direct SQL runs with their own credentials |
| Registry and runs Catalog.Schema | Shared metadata tables; users access them through Hub ACLs |
| Dedicated metadata SDK profile | OAuth M2M identity limited to Registry/history access; no business-table SELECT |
| Stable SQL review signing secret | Runtime secret store, never Git |
| Genie One knowledge + UC permissions | Company team installs relevant business assets/metrics |
| Mail sender authorization | Independent from Databricks; authorize company sender separately |

Genie One has no separate “MCP key” in this design. Its URL is derived from the
Workspace: `/ai-gateway/mcp-services/system.ai.genie_one_mcp`. The same individual
Databricks OAuth session authenticates SQL, Genie One and the lightweight router.
There are no A1/A2 Space IDs in runtime configuration. If the existing router model
service is unavailable in the company Workspace, leave its endpoint blank: manual
task creation stays available, and automatic parsing clearly reports unconfigured.

For `system.ai.genie_one_mcp`, confirm parent `USE CATALOG`/`USE SCHEMA`, service
`EXECUTE`, Workspace assignment and underlying business-table/view access. Model
service permissions are separate from MCP and SQL privileges. UC row filters and
column masks must be maintained by the company data team; Hub does not infer them
from email addresses, display names or editable owner fields. Do not grant users
raw access to the shared metadata tables containing other users' report snapshots.

## Deploy on the approved company computer/server

1. Clone the private repository on the approved network; use the maintained roots.
2. Create a Python environment; install the two requirements files. Build the UI:

   ```bash
   python -m venv .venv
   . .venv/bin/activate
   pip install -r business-ai-hub/requirements.txt \
     -r business-task-manager-v1/business-task-manager-v1/requirements.txt
   npm --prefix business-ai-hub ci
   npm --prefix business-ai-hub run build
   ```

3. Create the Registry/history tables from `database/` **after adapting the catalog
   and schema**. This is an explicit administrator step, not an application startup
   migration. Do not import the archived enabled Job or Alert definitions.
4. Adapt the separate Task Manager `settings.yaml` too: company catalog/schema,
   Registry/runs/outbox table names, mail configuration and schedule. Its current
   `business_date_offset_days: 487` is for the old simulated data; set **1** for
   the previous calendar day in the company environment. Do not carry the local
   previous-observed-day test SQL into production.

   Supply the values in `.env.example` using the approved server secret/config
   system. This app does not auto-load `.env`. Keep OAuth, Databricks M2M, Gmail
   secrets, refresh tokens and review signing keys outside Git and browser storage.
5. Configure the metadata profile outside Git using the SDK OAuth M2M credential
   format. Its host must equal the user Workspace host; mismatches are rejected.
6. Start one process behind the company HTTPS reverse proxy:

   ```bash
   cd business-ai-hub
   PYTHONPATH=.:../business-task-manager-v1/business-task-manager-v1 \
     uvicorn app:app --host 127.0.0.1 --port 8765 --workers 1 --no-access-log
   ```

   The server's loopback port must not be directly reachable by other clients.
   The proxy exposes only the configured HTTPS origin. Preserve ordinary cookies
   and Origin headers. Allow long analysis responses (up to eight minutes).
   Exclude callback query strings/codes and Authorization headers from proxy/APM
   logs. The app ignores forwarded identity/token headers in internal-server mode.
7. After administrator permissions are ready, enable `GENIE_ONE_ENABLED=true` and
   `TASK_CONDITION_SQL_ENABLED=true`, then log in using individual accounts.
   Keep `TASK_EXECUTION_ENABLED=false` and `TASK_EMAIL_ENABLED=false` until their
   respective integration acceptance and separate rollout approval.

One process is intentional: sessions and conversation/ticket ownership are in
memory. Restart requires login again; multiple replicas/workers require an approved
shared session store first. Shared metadata stays in Delta, not process memory.

## Network requirements

The user's browser must reach the internal HTTPS callback and company Databricks
sign-in/SSO. The server needs outbound HTTPS to the same company Workspace for
OAuth, SDK SQL and Unity Gateway MCP. If using Gmail it also needs Google OAuth
and Gmail API egress. VPN/private endpoints, DNS and IP allowlists depend on the
company architecture; no exact company domain can be assumed before IT supplies it.

## Short acceptance sequence

- Account A creates a draft; account B cannot list, read, edit, enable, trial or read
  its report/conversation. Changing owner JSON must not change authority.
- A and B query a controlled table with known UC row/mask rules. Results must match
  their Databricks access. Test denied access with no identity fallback.
- Generate one SQL draft with Genie One; review/test it. Subsequent SQL checks must
  issue no Genie calls. A false or unknown condition must create no report/email.
- Separately approve one real model/MCP call and one email delivery test; inspect
  timings, provider IDs, no duplicate sends and revocation behavior.
- Integrate the approved durable creator resolver, then separately enable scheduling.
  Logging in or activating a task never starts a Databricks Job.
