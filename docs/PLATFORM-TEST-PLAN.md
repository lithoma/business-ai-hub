# Business AI Hub：完整测试建议（待你审阅）

版本：2026-10-23。本文是建议，不是“全部已通过”的验收报告；本轮没有按本文批量调用模型、查询业务数据、启动 Job 或发邮件。你说的 GD1 在本文按当前统一业务入口 **Genie One** 理解。

## 先看这一页：建议怎么测

平台能跑通，不等于指标口径和业务结论已正确。建议分四层验收，每层分别留证据。

| 层次 | 必须回答的问题 | 谁给正确答案 | 当前可做 |
| --- | --- | --- | --- |
| 指标与数据 | 金额、分母、日期、品牌、聚合口径是否正确？ | 指标团队确认的定义和独立参考 SQL/固定结果 | 用模拟数据测结构；正式业务口径等指标团队 |
| Genie One | 是否找到正确的业务资产，并据此给出有证据的回答/SQL？ | 业务专家＋参考结果；不能只由另一个 LLM 打分 | 本地小样本手测；公司资源另验 |
| 产品流程 | 分流、草稿、条件、报告、邮件、页面状态是否符合预期？ | 本文案例的明确输入和结果 | 多数可本地测 |
| 权限与后台 | A/B 隔离、关闭网页继续运行、去重、撤权后权限是否生效？ | 双账号实测、执行身份和资源审计 | 边界可离线测；完整身份链需公司 |

**建议先测 6 条主线，再补异常，不先扩大测试数量：**

1. 明确数值条件的自然语言请求 → SQL 条件草稿 → 编辑 → 保存。
2. 同一任务分别命中 true / false → 只有 true 生成报告。
3. “异常”且无阈值的模糊需求 → 有依据的澄清或 AI 条件，不编造数值规则。
4. 已知答案的业务问题 → 核对指标、日期和最终回答。
5. 用户 A/B → 任务、报告、查询权限三方面分别验证。
6. 公司 Job Run as A → 关闭所有网页后执行；重复触发不重复生成报告。

第 1–4 条可以先在现有本地系统做；第 5–6 条中的真实权限效果必须等公司环境，不能拿共享试用或本地假用户冒充验收。会议 Demo 可只选 1、2、4，并展示其余测试计划。

## 测试前准备：统一答案、环境和证据

### 一份小型参考集

先准备约 10 个代表性业务问题，不要求立刻跑很多次。每题保存：

| 内容 | 要求 |
| --- | --- |
| 输入 | 原始业务问题、必要上下文、用户身份、业务日期 |
| 指标定义 | 指标名、定义版本、单位/币种、净额/毛额、时间字段、过滤维度、缺失值规则 |
| 正确结果 | 指标负责人核对的参考 SQL及结果，或业务专家明确的预期；固定到同一数据快照 |
| 正确行为 | 分析/任务/两者/先分析后任务/澄清；SQL或AI条件；应执行/应阻止 |
| 可接受差异 | 金额与比例舍入容差由指标定义决定；订单计数等应精确一致 |
| 证据 | 表/视图或 metric view 版本、查询引用、日期窗口、计算步骤和对应报告 |

参考集必须有两个业务领域的单域题和跨域题，但公司知识不由本项目复制或重建。Genie One 内部是否调用了原 A1/A2 不能凭界面猜测；只按可返回的来源和可验证结果判断。

### 环境边界

- **L：本地模拟/离线**——验证流程、日期算法、身份边界和失败处理；不证明公司数据准确。
- **D：当前开发 Workspace**——人工点击少量真实调用；模拟业务数据只能证明相应测试集。
- **C：公司 Workspace**——正式指标、两个真实用户、Apps OBO、原生 Job 和邮件权限验收。
- 每次记录代码版本/文件哈希、配置版本、Workspace、模型配置、数据快照及执行日期。不要把开发环境通过直接计入公司通过。
- 真实模型/查询由测试者明确触发；发信先预览并批准收件人；Job 保持暂停，先做一次手动运行再审批周期调度。

### 每条案例的记录模板

```text
case_id / 环境 / 代码与配置版本：
用户（脱敏标识）/ task_id / run_id / trace_id：
输入与业务日期：
```

真实业务问题、SQL和结果如需保存，应在公司批准的位置受控保存；下面的运行事件不收集原始 Token、密码、业务明细或邮件正文。

## A. 业务指标与 metric view 准确度

指标团队负责定义；我们负责把业务请求映射到正确资产、传递正确参数并保持执行/展示一致。不要让 Genie 回答同时充当唯一参考答案。

| ID | 输入/测试方法 | 预期与证据 |
| --- | --- | --- |
| M01 | 选一个日期/品牌，问 GMV、订单数、客单价 | 与同快照的参考值一致；单位和分母明确 |
| M02 | GMV、支付金额、退款后净额用不同问法 | 按正式定义区分；同义词映射正确，不能混用 |
| M03 | 报表总计与按品牌/渠道拆分 | 满足该指标的可加性；非可加指标不能简单相加 |
| M04 | 两层维度 join、重复订单、赠品等场景 | 无 join 放大/重复计数；赠品是否计入按口径解释 |
| M05 | 昨日、上一完整周、滚动7天、昨日对上周日均 | 四种窗口分别正确；周报周期不由标题猜测 |
| M06 | 月末、跨年、周一、闰日及上海午夜附近 | 日期边界、业务时区、本期/前期长度正确 |
| M07 | 上期为0、NULL、空表、缺失一天 | 按口径输出未知/不可比较；不能把未知当成0或正常 |
| M08 | 恰好下降10%、略高/略低于10% | 区分“超过”和“大于等于”；比较前不错误舍入 |
| M09 | 比率平均值、日均、客单价等 | 使用正确加权/分母，不对已聚合比例随意求平均 |
| M10 | 竞争/市场领域及销售跨域问题 | 使用有权限且语义兼容的资产；不同粒度先对齐 |
| M11 | 新增业务数据或修改 metric view 定义后重测一题 | 能识别版本差异；已有 SQL 的受影响范围明确，不能静默继续宣称旧语义正确 |
| M12 | 模拟数据每3天一条 vs 公司每日数据 | 临时“上一有数据日”只用于标注的测试任务；生产不静默沿用 |

**准确度建议分开统计：** 指标数值一致率、日期/维度一致率、口径引用正确率、未知场景处理正确率。没有正式参考定义时标“无法判断”，不要计为通过。

## B. Genie One（GD1）回答和 SQL 的质量

建议首轮每类只选一个代表题。只对不稳定或修改过的题追加重复，避免无目的消耗。

| ID | 问题类型/操作 | 通过标准 |
| --- | --- | --- |
| G01 | 有确定答案的单域指标问题 | 数值、日期、维度和来源均与参考集一致 |
| G02 | 同一问题的中英文、简称、业务别名 | 语义与结果一致；不能因措辞改变指标口径 |
| G03 | 竞争/市场题与赠品题 | 使用公司已有的合适语义资产；不因旧 A1/A2 名称消失而失去能力 |
| G04 | 跨销售与竞争的综合问题 | 可核对每段来源和粒度；无权限或缺数据时明确说明 |
| G05 | “昨天为何下降？” | 观察事实与因果推断分开；解释有证据，不编造促销/库存原因 |
| G06 | “异常时通知我”，没有阈值 | 按需求澄清，或构建有证据要求的 AI 条件；不随意发明阈值或默认正常 |
| G07 | 多轮先分析再要求设置任务 | 日期、品牌、指标与用户确认的发现正确传入草稿；不误引用旧会话 |
| G08 | 请求查询无权访问的数据、或用聊天要求创建 Alert/Job | 数据权限生效；业务对话不绕过平台审核创建原生 Alert/Job；需要公司验证 MCP 工具策略 |
| G09 | 相同输入必要时重复2–3次 | 比较关键事实/SQL含义是否稳定，而非逐字一致；记录额外调用量 |
| G10 | 返回 SQL、结构化查询来源或缺乏结构化结果 | 只采用可核验的 SQL 来源；不能从漂亮的回答文字猜测已经执行的 SQL |

建议业务评分每题记四项：**数值事实、口径与来源、推断边界、可操作性**，各用“正确/部分正确/错误/无法判断”。禁止仅靠“回答看起来合理”或另一模型的总分通过。

## C. 分流、自然语言设置和 Task 生命周期

| ID | 输入/操作 | 预期结果 |
| --- | --- | --- |
| T01 | “善存昨天 GMV 是多少？” | 只分析；不创建 Task |
| T02 | “每天9点，善存 GMV 下降超过10%时生成报告” | 任务草稿；SQL 数值条件，时间/时区/阈值/方向正确 |
| T03 | “分析竞品上周变化，并每周五给我报告” | 独立部分可并行；任务与分析清楚呈现，不重复保存 |
| T04 | “先找下降最明显的品牌，再每天检查它” | 先分析再据确认结果生成任务，不提前猜品牌 |
| T05 | “缓存/销售异常时报告” | 澄清对象或定性 AI 条件；缺少表结构不自动改成AI来掩盖缺口 |
| T06 | 无 endpoint、模型403、输出不合法或缺必填字段 | 明确错误，手动创建可用；不展示 mock，不保存半成品或自动重试付费调用 |
| T07 | 自动 SQL 失败、手动修改、重新生成局部 | 保留已有草稿；仅补对应步骤，不重复整轮分析/保存 |
| T08 | 保存后刷新、重复点击保存、两个窗口编辑同一版本 | 持久化且不重复；旧版本更新被拒绝，有可理解提示 |
| T09 | 草稿→审核启用→暂停→编辑→删除 | 审核需完整配置及有效条件测试；修改 SQL/窗口需重测；暂停后不领取新执行 |
| T10 | 列表、统计、筛选、分页、对话内操作 | 状态和计数一致；对话内保存后任务页更新；启用不伪装成调度已启动 |
| T11 | 时间选择与自然语言生成时间 | 界面只提供当前支持的每日/每周/间隔整点；不展示每小时业务，不新增后台强制限制 |

## D. 条件 SQL 和 AI trigger

| ID | 输入/操作 | 预期结果 |
| --- | --- | --- |
| Q01 | 明确数量/同比/阈值条件 | 优先生成 SQL；带正确日期绑定，保留可编辑预览与来源 |
| Q02 | 已保存 SQL 换两个业务日期执行 | 直接重用 SQL；不再调用 Genie 重新生成 SQL |
| Q03 | 返回 true、false、NULL、字符串"true"、多行/零行 | 严格按 BOOLEAN 合约处理；SQL BOOLEAN 被驱动编码为 true/false 字符串可解析，SQL VARCHAR不冒充BOOLEAN；未知/错误不生成报告 |
| Q04 | DDL/DML、多语句、外部/远程或AI函数等不允许结构 | 执行前拒绝；还需限制 Genie MCP 工具侧写能力，应用 SQL 校验不能代替它 |
| Q05 | 任意修改 SQL、比较窗口、切换用户后复用测试凭证 | 原测试凭证失效或拒绝跨用户使用；审核不能跳过重测 |
| Q06 | 超时、Warehouse停止/冷启动、查询失败、截断 | 有明确失败；不据无结果判断“不触发”，不自动重提查询/生成报告 |
| Q07 | 定性 AI 条件分别有正向、反向、不足证据样例 | 返回严格 true/false 与依据；无法判断时保留未知/错误，不臆断 |
| Q08 | 条件 false/unknown 后跟踪调用事件 | false 不进入报告/发信；unknown 标失败且不发信，而非标正常 |

**“执行成功”只能证明 SQL 合法且完成，不能证明口径正确。** Q01/Q02 的业务正确性仍需 M 类参考结果验证。

## E. 身份、数据权限、Task/报告隔离

准备公司用户 A、B：对部分数据有不同权限，并各有自己的 Task。测试者应有办法核对 Databricks 审计记录或查询身份；不能只看页面上显示的姓名。

| ID | 操作 | 通过标准 |
| --- | --- | --- |
| A01 | A、B 分别从同一 App 链接登录 | 只部署一个 App；各自实际 Databricks 用户ID和业务 SDK 不同 |
| A02 | A、B 问同一条受限数据问题 | 各自实际资源权限和行列策略生效；有权限相同也可以结果相同，不人为制造差异 |
| A03 | B 猜测 A 的 Task、run、report ID，直接调用读/改/删/启用/发信 API | 无法获得或操作 A 的记录；不能靠隐藏按钮当权限控制 |
| A04 | 修改前端 owner/security、邮箱、Workspace、会话ID、SQL测试凭证 | 不改变执行身份；跨用户票据/会话/凭证无效 |
| A05 | 用户缺少某项 scope、表权限、Warehouse CAN_USE、MCP EXECUTE | 明确拒绝，不回退 App/SP/CLI；只报告上游明确给出的缺失项 |
| A06 | 丢失用户令牌、过期、跨站修改、错误平台入口 | 请求被拒绝；本地伪造转发头不能作为公司身份验收 |
| A07 | 关闭浏览器/退出网页 vs 撤销 App访问权/停用用户 | 关闭网页不应阻止原生 Job；真实撤权须生效，两者分开验证 |
| A08 | App 存储身份与用户业务身份 | App只承担元数据授权；业务 SQL/Genie调用记录为创建者，无共享大权限兜底 |
| A09 | 不同用户同时执行、线程交错、轮询令牌更新 | SQL和报告各阶段维持各自创建者；无串号或缓存串用 |
| A10 | 用户权限在 Task 创建后、运行前或条件后变化 | 下一次受限操作按当前权限处理；不保留创建时权限快照；报告阶段也检查身份 |

首轮安全底线：**任何跨用户读取/修改/身份替换成功都阻止公司上线**；普通业务回答的准确度分数不能抵消这类失败。

## F. 真正的定时与离线执行

此处“离线”指员工不在线，App/Databricks服务仍在线。配置与入口见 `CREATOR-JOBS.md`。

| ID | 操作 | 预期与证据 |
| --- | --- | --- |
| J01 | Job模板/配置离线检查 | PAUSED、Run as创建者、并发1、无自动重试；不创建计算资源，不含凭据 |
| J02 | 公司手动运行一次暂停的 Job，全部网页关闭；必要时重启 App 清空旧会话 | 从本次 Notebook身份换取App令牌并执行；不依赖浏览器refresh token或旧内存缓存 |
| J03 | 同一创建者两个 Task，其中一个未来到期/暂停/草稿 | 只执行 active、enabled、当前到期的任务 |
| J04 | 同一 slot 重复触发两个请求/Job run | 只生成一次报告；明确复用已有 run，失败也不静默重做 |
| J05 | 一个用户三个以上到期 Task | 前两个执行，其余明确未认领再分批；无丢失、无重复、总等待有上限 |
| J06 | 将 Job Run as 改成 B、subject/job绑定填错、使用共享SP请求 | 不能执行A任务；在业务调用前拒绝，日志不泄露报告内容 |
| J07 | 持续运行跨 App令牌刷新时间、用户无网页会话 | Job按本次运行凭据更新短期App令牌，App继续按该用户执行；公司端必须实测 |
| J08 | Job→App请求超时/断网，或App在生成中重启 | 不确定提交不自动重发；认领账本防重；中断明确失败/待核对，不伪造成功 |
| J09 | 业务日跨午夜、每周五、间隔天数、未来开始日 | 采用 Task 时区/业务日期；不自动补跑过去日期；频率与报告窗口分别验证 |
| J10 | 获批后真正开一次周期触发 | 记录计划时间、Job实际启动、App收到、SQL开始、报告完成；区分启动延迟和业务计算耗时 |
| J11 | Job/cluster停止、Warehouse停止、App不可用、用户撤权 | 各类失败原因能区分，不切身份，不自动扩大资源/权限 |
| J12 | 已审核任务跨过条件测试凭证的7天有效期 | 未修改的active任务可继续；新启用用旧凭证仍被拒绝；改SQL/条件/窗口或换创建者仍不能复用凭证 |

默认小时检查器不等于小时业务；由于当前界面只支持整点，可先据此测试。Job 启动/计算/SQL Warehouse 冷启动意味着不能承诺秒级准时。先测一次手动原生 Job，再考虑开周期；不为测试“加速时间”而改变真实生产时钟。

## G. 报告、模板与邮件

| ID | 操作 | 通过标准 |
| --- | --- | --- |
| R01 | 条件成立生成报告 | 主指标、品牌、日期、触发理由与SQL结果一致；不额外捏造未核验的指标 |
| R02 | 要求“上周完整周报” | 内容确实覆盖完整周和对比窗口，不能仅标题写周报而正文只分析单日；这项应重点复验 |
| R03 | 刷新、分页、查看旧报告 | 不重新调用模型；只有对应用户可见，执行/通知状态分开 |
| E01 | 预览但不发送、内容修改后使用旧指纹发送 | 预览不发信；旧指纹被拒绝；收件人/抄送受允许名单约束 |
| E02 | 条件false、unknown、查询失败 | 均不发报告邮件；unknown保留错误信息 |
| E03 | 获批的一封测试邮件、双击发送、超时不确定后再点 | 一次认领一次尝试；EMAIL_ACCEPTED与收件箱已收到分开记，EMAIL_UNKNOWN不自动重发 |
| E04 | 原生 Job 生成报告但未批准自动投递 | 只生成报告；当前代码明确 automatic_email=false，不能把它当成自动邮件已完成 |
| E05 | 公司模板、CSV导出（后续接入时才执行） | CSV由获批标准SQL产生，权限仍是创建者；编码/字段/行数/附件大小符合模板；不为传附件额外调用Agent |

目前不要求我们设计公司复杂报告模板或重建指标知识。模板/CSV尚未接入时标“未开放”，不要把相关用例记为通过或阻止当前核心演示。

## H. 页面、可操作性与每个功能事件

### 页面手测

1. 桌面和窄屏各走一次主线：输入框、主按钮、流程图、草稿及错误提示可见，弹窗不遮挡关键操作。
2. 用户能从页面分清：生成建议、保存草稿、审核启用、执行中、报告完成、邮件接受；不让“App running”暗示 Task 调度已开启。
3. 失败后保留已填内容，支持局部修复，不迫使整轮重新调用。
4. 当前 Haleon 配色下检查正文、表单、禁用按钮和状态提示的可读性；颜色之外仍有文字说明。
5. 操作人无需理解 SQL SDK、MCP 或 Token 才能完成正常任务；技术错误留可读摘要和可关联的运行编号。

### 建议核对的事件链

以下是**验收时应能解释的业务事件**，不是宣称它们都已按这些名字实现了日志。现有埋点主要是 HTTP请求、SDK/MCP span、run阶段与耗时；表中注明实际承载或缺口。

| 事件/阶段 | 应观察什么 | 当前证据/待补充 |
| --- | --- | --- |
| 登录成功/拒绝 | 模式、用户脱敏标识、Workspace、HTTP状态；无Token | session/鉴权响应；公司平台审计另核对 |
| 收到业务请求 | trace_id、request_id、起止、接口、状态、响应大小 | 本地 telemetry requests 已有 |
| 分流结束 | 路由类型、耗时、解析模型、调用数 | 路由响应/流程图；长期结构化路由结果日志需补充 |
| 分析开始/完成/失败 | Genie会话/响应引用、MCP调用次数和等待 | MCP span/接口响应；内部Agent选择不可猜测 |
| 草稿提议/编辑/保存 | 是否保存、任务版本、校验错误 | HTTP与Registry状态；编辑审计历史未完整实现 |
| SQL生成/测试 | 来源、参数窗口、statement_id、真假或错误、耗时 | SQL/MCP span、测试结果和签名凭证 |
| AI条件测试 | 证据引用、严格判断、未知原因 | 条件测试结果；业务正确性另人工核对 |
| 审核启用/暂停 | 操作人、前后状态、版本 | 生命周期API与Registry；完整变更审计可后续补充 |
| Job启动/令牌交换 | Job/run引用、成功/HTTP类别、交换耗时 | Notebook最终摘要有总耗时；单独交换耗时尚待细化 |
| 到期/认领/去重/延期 | slot、run_id、是否复用、DEFERRED未认领 | run ledger和dispatch响应；Job/run关联为请求注记，服务端未核验run_id真实性 |
| 条件检查/报告生成 | phase、condition/report/total耗时、最终状态 | run artifacts timings 已有 |
| 邮件预览/发送 | 指纹、收件范围、通知状态、提供商回执、耗时 | 邮件API/运行记录；不把正文放普通事件日志 |
| 跨用户/权限拒绝 | 403/404、阶段、错误类型 | API结果和平台审计；不输出被拒绝资源的内容 |

**事件顺序检查：** 没保存就不应出现“审核启用”；没命中条件就不应有报告调用；没预览确认就不应出现当前手动发信；去重请求不应再次产生模型/邮件副作用。并行分析和草稿可以交错，但都应关联同一次用户操作。

## I. 时间、资源与费用测评

用户体感速度和模型准确度分开看。首轮先记录少量真实样本，不为凑统计量批量调用。

| 测量 | 记录方式/解释 |
| --- | --- |
| 页面到可编辑草稿时间 | 浏览器操作到表单可用；区分轻量解析和后续SQL生成 |
| 普通分析、SQL生成、SQL执行、报告生成 | 各阶段独立计时；不要把嵌套SDK span相加当总耗时 |
| 定时迟到 | 计划时刻→Job启动→App接收→条件完成，分别记录 |
| 模型/MCP/SQL数量 | 应用观察到的调用量；缓存/去重前后比较，MCP轮询不算新提问 |
| token与费用 | 只记提供商真实返回值；Genie内部token、Warehouse DBU、Job计算费查不到时记未知，不记0 |
| 冷/热运行 | Warehouse/Job计算环境冷启动与已运行各记一例，不能混为代码速度退化 |

已有本地数据可通过界面测试记录导出或 `HUB_TEST_METRICS_DB` 对应 SQLite 查看；该数据库在用户本机状态目录，不进入Git/ZIP。共享试用不允许访客导出全部本地测试记录。浏览器渲染/用户思考时间不在后端HTTP计时中，需单独测量。

不要现在承诺统一延迟或成本目标。先获得冷/热样本，再由你选择可接受范围；样本少时列原始耗时，不报没有统计意义的p95。

## 建议验收顺序与判定

| 阶段 | 最小范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1 本地主线 | 6条主线中当前能测的部分＋历史正反日期 | 草稿/SQL/报告状态一致，未误发送 |
| 2 业务正确性 | 10题小参考集＋关键边界 | 指标负责人认可口径；关键事实错误已修复或明确阻止执行 |
| 3 公司权限 | A01–A10中的关键身份/跨用户/撤权案例 | 无越权，无共享身份兜底，实际调用身份可核对 |
| 4 后台小型烟测 | J02、J03、J04、J06、J08 | 无网页可执行；重复无副作用；失败不扩大权限或重放 |

**阻止上线的情况：** 跨用户泄露；写业务表；关键指标/触发方向错误仍允许执行；条件未知被当正常；重复发信；执行身份与创建者不符；把mock或未验证结果展示为真实成功。

**可记录后续改进的情况：** 不影响操作的细节样式、非关键措辞、明确提示的未接入CSV/公司模板、尚无足够样本的性能目标。具体优先级由你审阅后调整，不用为了“覆盖率数字”添加大量实现镜像测试。
